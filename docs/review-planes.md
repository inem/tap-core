# Review lenses

Граф зависимостей ([трекер #1](https://github.com/inem/tap-core/issues/1), [M1](https://github.com/inem/tap-core/milestone/2)) показывает, какие результаты нужны следующему срезу; он не требует ждать полного закрытия каждой входной задачи. Он **не** проверяет правильность границ: можно собрать всё в верной последовательности и получить pack, который нельзя отдельно отключить или который берёт credentials соседнего компонента.

Ниже — не ортогональные оси и не формальный базис (ответственность, процессы, состояние, права, поставка пересекаются). Это ракурсы проверки — вопросы, которые уже ловили реальные дефекты. **Прогонять каждый PR через шесть обязательных отчётов не нужно: автор отмечает затронутые ракурсы, ревьюер проверяет пропущенные.**

## Ракурсы

| Проверяем | Основной вопрос |
|---|---|
| Сценарий и зависимости | Что теперь может сделать пользователь и какие входы нужны? |
| Ответственность | Кто владеет поведением; где кончается core и начинается pack? |
| Исполнение и состояние | Кто запускает, останавливает, хранит прогресс и восстанавливается? |
| Доступ и эффекты | Какие полномочия реально доступны; что при повторе или неопределённом результате? |
| Поставка и совместимость | Что независимо ставится, обновляется, отключается, удаляется? |
| Доказательства | Что проверено: fixture, replay, live, установленный артефакт, чистый Mac? |

Отдельно для переносимого legacy-кода — **происхождение и право публикации**.

## Противоречие ≠ незавершённость

На промежуточном срезе часть решений может отсутствовать в пределах явно заявленного scope. Для каждого изменения различать, не смешивая:

- **обещано** — что изменение утверждает доступным сейчас;
- **подтверждено** — какой проверкой (fixture / replay / live / установленный артефакт / чистый Mac);
- **ещё не сделано** — и в каком тикете будет.

Противоречие между обещанным и фактическим поведением — дефект. Невыполнение обязательного критерия приёмки тоже не позволяет объявить задачу завершённой. Допустимый остаток среза должен иметь явные границы и владельца; ссылка на будущий тикет сама по себе не отменяет требования текущей задачи.

Виды проверок не образуют единую лестницу: живой прогон не заменяет replay/parity или проверку восстановления. Для каждого утверждения нужны соответствующие сценарий, версия и результат.

Пример: общий HTTP-клиент сам по себе границу доверия не нарушает. Нарушение — если обещаны **раздельные** права search/rename, а фактически выдан общий полный доступ к одним credentials. Общая библиотека совместима и с раздельными правами, и с явно принятой общей областью доверия — выбор надо **назвать**, а не подразумевать.

## Итог по каждому ракурсу

Для затронутых ракурсов достаточно краткого обоснования в описании PR; отдельный отчёт по каждому не требуется. Найденный пробел заканчивается одним из: **исправление · явно принятое ограничение · конкретный тикет**. Не молчаливым «потом».

## Три ветки экосистемы

- **A · capture / data** — capture → readers. Работает без браузера.
- **B · browser / control** — inject → WS-мост → handlers. Не требует сохранения capture-записей и запуска readers; перехват страницы для инжекта остаётся отдельной зависимостью.
- **C · applied commands / consumers** — search/fork/rename + organizer ([#25](https://github.com/inem/tap-core/issues/25)/[#26](https://github.com/inem/tap-core/issues/26)). Capture и WS-мост не являются обязательными зависимостями каждой команды. Organizer может потреблять результаты capture/readers; зависимости устанавливаются по конкретному сценарию.

Приёмка связанного example ([#14](https://github.com/inem/tap-core/issues/14)) требует A + B; не каждый pack обязан использовать обе ветки. [#32](https://github.com/inem/tap-core/issues/32) отвечает за жизненный цикл выбранных компонентов профиля. Ракурсы применяются к изменению в любой из веток — ветка не освобождает от вопроса о правах, состоянии или поставке.
